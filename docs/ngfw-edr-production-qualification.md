# EDR / AuditD: допуск конфигурации к ограниченному продовому пилоту

Статус: инструменты и порядок испытаний. **Результата GO пока нет.**
Цель — измерить работу NGFW и сохранить полезные события EDR. PR, CI,
активный сервис и количество событий сами по себе не отвечают на этот вопрос.

## Обязательный маршрут

1. Одна поставка инструментов через PR → CI → merge → интерактивный Ansible pull.
   Проверить установленную ревизию и образ endpoints. Apply не запускает кампанию.
2. Один T00 на campaign/topology: offline snapshot и проверяемый rollback;
   при выключенном NGFW исправный receiver недоступен клиенту; после включения
   управление/dataplane исправны; старой нагрузки нет; EDR зарегистрирован и
   подключён центрально; AuditD active, lost=0, runtime B/boot/config hashes сохранены;
   нет immutable/panic/halt; ресурсы обоих endpoints известны.
3. На неизменном B калибровать TCP 100/300/600/900 Мбит/с (4–8 потоков),
   UDP 64-byte 20/60/100 Мбит/с, short-TCP 500/1000/2500/5000 CPS,
   затем отдельно HTTP/DNS 200/500/1000/2500 операций/с.
   Warmup 30 с, measure 120 с, recovery 60 с. Нужен фактический PPS приёмника.
   В iperf3 `packets` — верхний sequence number; PPS отчёта использует
   `(packets - lost_packets) / seconds`, а не номинальную скорость отправителя
   ([семантика счётчиков iperf3](https://github.com/esnet/iperf/blob/master/src/iperf_udp.c)).
4. Выбрать рабочие нагрузки около 70–85% максимальной устойчивой фактической
   производительности. Проверить выбранные ступени; недостигнутая скорость —
   ограничение измерения, а не доказанный предел NGFW. Зафиксировать, какие
   сценарии этот стенд не может валидно сгенерировать.
5. На одинаковой работе выполнить B/C-EDR-NET/B и B/C-EDR-PROC/B.
   Проверить исчезновение именно целевых keys и точный возврат B.
6. Только по данным сформировать D: сохранить запуск процессов, привилегии,
   системную/NGFW-конфигурацию, время, критические файлы и EDR.
   Исключить только доказанно дорогие группы с принятой потерей телеметрии.
7. Получить A-NO-EDR из чистого клона/snapshot до установки агента.
   Остановка службы не создаёт чистый A. При тех же ресурсах, политике,
   топологии, генераторе, наблюдателе и forwarding выполнить A/B/D/A,
   минимум три валидных повтора каждого workload.
8. Проверить независимые центральные receipts для тестового события, процесса,
   административного действия, конфигурации, привилегии и времени, если оно
   включено в модель. Локальная запись или active vxagent не заменяет receipt.
9. Endurance D: 30 минут → восстановление → 60 минут на выбранной ступени.
   Для полного 60-минутного окна открыть измерительный брокер с явным
   `--lifetime 7200`; его стандартных 1800 секунд недостаточно даже без прогрева.

H3–H9 — диагностический резерв после основных сравнений либо для конкретного
runtime-блокера. Новый PR после поставки допустим только для дефекта, делающего
данные недействительными. Невозможность безопасно сменить правила блокирует
ablation, но не калибровку на B.

## Запуск и остановки

На KVM-хосте в `/srv/apps/ngfw-lab` есть четыре отдельных плана в `plans/`.
Команда `plan` ничего не запускает:

```sh
python3 runner.py plan --qualification-plan edr-calibration \
  --campaign-id edr-qualification-01 --audit-profile B-EDR-CURRENT
```

Для однократного `check-isolation` и последующих `run` передавать ту же пару
`--qualification-plan edr-calibration --campaign-id edr-qualification-01`.
Уже полученное старым инструментом T00 не подделывать: `bind-isolation` с теми же
параметрами плана и `--unchanged-campaign-attestation EVIDENCE_REFERENCE` сверяет
фактическую topology и содержание отрицательной проверки, сохраняет отдельную
привязку по hash, не меняя исходный артефакт и не запуская трафик. Аттестация
оператора подтверждает отсутствие смены VM/snapshot/маршрута с момента T00.
Новый T00 повторять при изменении campaign,
маршрута, topology, VM или snapshot, а не по истечении суток.
Все qualification-run требуют приватные `--measurement-config`,
`--measurement-argv-file` и `--run-context`; campaign/profile в них совпадают.

Для остальных планов нужен `--selected-workloads /private/selected.json`:

```json
{
  "calibration_run_ids": ["ACTUAL_RUN_ID"],
  "selection_reason": "Actual stable limit and 70-85% working-range evidence",
  "scenarios": [{"name":"tcp-working","kind":"tcp","mbps":100,"parallel":4}]
}
```

Число 100 здесь — пример структуры, не выбранная по данным нагрузка.
Использовать один и тот же файл во всём сравнении. Endurance запускается
отдельно с `--endurance-minutes 30`, затем `60`, после проверки восстановления.

| Результат | Действие |
| --- | --- |
| WARN, ошибки <0,1% | Сохранить окно, recovery, повторить ту же ступень один раз |
| SCENARIO_STOP, 0,1–1% или повторные ошибки | Остановить лестницу данного kind; recovery и свежий health-check перед независимым kind |
| GLOBAL_STOP, ≥1%, ноль успешных операций, lost, опасный backlog/диск/память, недоступность | Прервать всю кампанию, сохранить окно |
| INVALID, генератор <95%, метрики/условия неполны | Не использовать окно для предела NGFW; прекратить повышение этого kind |

CPU 95–100% в qualification — наблюдение. Упор endpoints в выделенную квоту
или общего хоста делает окно непригодным для оценки NGFW. Температура не входит
в аналитический вердикт; применяются только заранее выбранная аварийная граница
`temperature_stop_c` и реально выросшие аппаратные throttling counters.
Requested/attempted/successful rates различаются; компенсирующего burst нет.

## Смена правил в госте

`audit_profile_ctl.py` устанавливается Ansible на хост как операторский файл;
для использования передать проверенную копию в приватный каталог **гостя**.
Запускать от root только в изолированном `pt-ngfw-auditd`, не на гипервизоре.

`inventory` читает auditctl -l/-s, boot ID, hashes файлов и состояния сервисов.
`plan --profile C-EDR-NET --expected-hash HASH` печатает точный diff.
NET исключает только `pt_siem_api_socket/connect/accept/listen/bind`;
PROC — только `pt_siem_proc`. Смешанный ключ или неизвестный формат блокирует apply.

`apply` требует новую резервную копию в существующем приватном каталоге 0700,
`--backup /private/B-original.json`, `--timeout SECONDS` и последним аргументом
`--command` с явной ограниченной командой удержания/испытания профиля.
Он сохраняет B с 0600, проверяет свежий hash, применяет C и всегда восстанавливает
B после команды, её ошибки, timeout, SIGINT или SIGTERM. Для host-side runner
оператор согласует длительность guest-side удержания и завершает его после run;
если B вернулся внутри измерения, inventory-hash делает сравнение невалидным.

Восстановление: удалить по полному совпадению сохранившийся суффикс после первого
пропуска и добавить оригинальный суффикс в исходном порядке. Это означает короткий
переходный интервал восстановления без части правил; в нём **не измерять нагрузку**.
Глобального `auditctl -D`, перезапуска EDR, правок auditd.conf, forwarding,
failure/backlog, persistent rules или `audit=0` нет.
Метод адресного удаления требует точного совпадения правила согласно
[официальному auditctl](https://github.com/linux-audit/audit-userspace/blob/master/docs/auditctl.8).
До первого ablation подтвердить plan/restore на runtime этого гостя.

`restore --backup ...` и `verify --backup ...` проверяют равенство **строки и порядка**
runtime B, boot ID, файлов и фиксированных AuditD controls. Чужой дрейф вызывает
явный отказ, а не удаление неизвестных правил. SIGKILL, потеря питания или
недоступность auditctl требуют ручного восстановления из backup/snapshot;
постоянные файлы инструмент не меняет. Если точное восстановление не доказано,
оставить B и продолжить только calibration.

Числовой `filetype` из `auditctl -l` преобразуется в соответствующее имя только
в аргументах удаления/добавления (`32768` → `file`); исходный текст, хеши и
проверка порядка остаются без преобразования. Неизвестный тип блокирует plan до
любого удаления. Это требуется парсером
[libaudit 3.0.9](https://github.com/linux-audit/audit-userspace/blob/v3.0.9/lib/libaudit.c).

D поддерживается только с `--candidate-file`: `baseline_sha256`, `removed_keys`,
`ablation_run_ids`, `telemetry_acceptance_evidence`, `rationale`.
Это объявленные обоснования оператора, не автоматическое подтверждение пользы.
Допустимы только исследованные NET/PROC keys. A инструментом не создаётся.

## Анализ и критерии допуска

`campaign.py --mode calibration|net|proc|confirmation|endurance --runs DIR ...`
проверяет артефакты и сравнимость. Старый `--mode legacy-h2` сохраняет полный
A/B/C-NET/A и критерий ≥70% добавленной CPU-стоимости без ослабления.
Экспорты `audit_evidence.py summarize` дают фактические EPS/bytes/s/events_by_key;
`compare` сопоставляет source/receiver записи по digest.
Дополнительный `--evidence` передаёт приватный bundle этих экспортов, receipts,
происхождения чистого A и решения по D; анализатор помечает его как **declared**,
не присваивает причинный вердикт автоматически. Неполученные данные остаются null/gap.

GO допустим только для указанной политики и проверенного диапазона:
полезная скорость/CPS/PPS D не хуже A более чем на 5%; p95 не ухудшается
одновременно >10% и >5 мс; UDP loss ≤0,5% и не хуже A; ошибки не растут;
management/dataplane доступны; lost=0; backlog разгружается; диск безопасен;
EDR подключён, все обязательные receipts получены; B восстановлен;
есть ≥3 повтора и endurance 30/60 минут. Иначе CONDITIONAL GO с точными
непройденными ограничениями либо NO-GO; отсутствие основных доказательств — NO-GO.

Итог начинать с H1/H2, стоимости PROC, полной стоимости EDR против A, состава D,
максимальной фактической нагрузки, критериев, сохранённых событий и ограничений.
Только затем перечислять local / Git / CI / deploy / live по отдельности.
Доля PROC в событиях не равна доле CPU; отсутствие эффекта NET в проверенном
диапазоне допускает NOT_SUPPORTED_IN_RANGE или INCONCLUSIVE без бесконечного поиска.
