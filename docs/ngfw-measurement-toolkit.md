# Измерители и живая панель NGFW / AuditD

Текущий приоритет — [проверка EDR для продового пилота](ngfw-edr-production-qualification.md):
калибровка на B, B/C-NET/B, B/C-PROC/B, затем чистый A/B/D/A и endurance.
Панель и H3–H9 не должны вытеснять эти измерения.

`campaign.py` имеет отдельные `--mode calibration`, `net`, `proc`, `confirmation`,
`endurance`; старый `legacy-h2` по-прежнему требует полный A/B/C-NET/A.
Новые режимы отвергают дрейф нагрузки/наблюдателя/восстановления и не выдают
автоматический причинный SUPPORTED или production GO. В отчётах есть фактическая
работа, ошибки/потери/квантили, CPU VM и доступных процессов, disk I/O, backlog/drain,
lost, здоровье и forwarder. Неполученные EPS/keys/центральные receipts обозначены
явными gaps; `--evidence` принимает объявленные дополнительные доказательства
для последующей независимой проверки.

`audit_evidence.py summarize` дополнительно даёт `events_by_key`, `audit_eps`,
`audit_bytes_s` для неизменяемого экспорта конкретного окна. Количество записей
отличается от числа уникальных событий; доля событий не оценивает стоимость CPU.
`audit_profile_ctl.py` — отдельный guest-side инструмент inventory/plan/apply/verify/restore;
он не вызывается runner или Ansible автоматически. Его границы восстановления
и приватного backup описаны в операторском документе.

Набор расширяет [методику H1–H9 / T00–T20](ngfw-audit-performance-plan.md).
Это код измерений, а не заявление о готовности стенда. Развёртывание,
T00, источник событий, пороги и отсутствие влияния наблюдателя проверяются отдельно.
Нагрузку, правила AuditD, политику NGFW и отказ получателя панель не включает.

### Что остаётся ручным или BLOCKED

- T00: snapshot/откат, отрицательная проверка изоляции, охлаждение, фактические
  IP/датчики/диск/имена процессов, сверка часов и пробный малый прогон. Это невозможно
  подтвердить на выключенном сервере. `measure-check` не выдаёт READY.
- T11: выбрать безопасные административные действия, ожидаемые события и подтвердить
  их наличие после C-NET. Анализатор не угадывает, какие события должны существовать.
- T13/T15-F/T19: утвердить единственную разницу правил/flush/штатного логирования,
  применить отдельно и сохранить read-back. Эти изменения не автоматизированы измерителем.
- T14: `wchan` и audit wait counter дают наблюдение, но могут не доказать ожидание
  конкретного процесса в audit-пути; без атрибуции вывод H4 остаётся PARTIAL/INCONCLUSIVE.
- T16: нет автоматического fault injection. Требуются выделенный приёмник/путь,
  отдельное разрешение, лимит ≤30 с, запас места и подтверждённое дренирование.
  Точный возраст старейшего сообщения и размер всех очередей в байтах данные версии
  не дают. Если критерий опыта требует их, он BLOCKED, не заменяется нулём или
  возрастом файла. Останавливать общий коллектор нельзя.
- T18/T20: значения по умолчанию установленной версии, vendor debug/capture/offload,
  хэш опубликованной политики/версия appliance — отдельные фактические evidence.
  Автоматического доказательства причин падения по корреляции нет.
- Для сценариев файлов/exec нужен согласованный ограниченный источник именно этих
  событий: сетевой генератор сам по себе не гарантирует T05/T06. Не запускать
  произвольные syscall/file flood на appliance; сначала T02.

## 1. Развёртывание и read-only discovery

Доставка — штатный Git → CI → main → локальный Ansible. Роль `ngfw_lab` копирует
инструменты в `/srv/apps/ngfw-lab`, но **не запускает** ни тест, ни web UI.
Пароли/приватные argv и evidence не коммитить. На abykovserv не требуется sudo от агента.
Не расширять sudoers гостя ради удобства измерений.

Для гостя с интерактивным входом и sudo использовать
[одноразовый read-only канал](ngfw-interactive-probe.md): без host sudo, новых
ключей, изменения sudoers или сохранения паролей. Канал фиксирует варианты
пробника на время сеанса и прекращает выдачу данных при потере гостя.

Альтернативно на хосте нужен уже согласованный неинтерактивный доступ в гостя для чтения AuditD.
Приватный JSON argv заканчивается отдельными `"python3", "-"`: пробник передаётся
через stdin, не устанавливается в appliance. Например, через уже разрешённый
гостевой sudo `-n` (без пароля в файле/аргументах):

```json
["ssh", "-T", "-o", "BatchMode=yes", "-o", "StrictHostKeyChecking=yes", "-o", "ConnectTimeout=3", "ngfw@10.77.0.20", "sudo", "-n", "python3", "-"]
```

Это **не настройка доступа**. Если такой доступ не подготовлен, read-only сбор
завершится ошибкой и нагрузка не запустится; согласовать доступ отдельно.
Использовать ранее проверенную идентичность/ключ и host key.

```bash
cd /srv/apps/ngfw-lab
python3 runner.py measure-check --measurement-argv-file /private/guest-probe-argv.json
```

`readiness.json` сохраняет доступные датчики, устройства, счётчики, версии и причины
BLOCKED. Отсутствующее действие auditd не считается безопасным default: требуется
read-back/проверка документации установленной версии, без самовольной правки.
Пробник читает метаданные audit.log, не его содержимое; процессы выбираются точным
Linux comm (≤15 символов), без cmdline/environ.

### T20: не превращать пробник в основной источник аудита

Если действующий профиль аудирует чтения `/proc`, поиск процессов через
`/proc/*/comm` сам создаёт AuditD-события. Низкое собственное CPU-time пробника
не означает низкую стоимость порождённого им аудита. До сравнения профилей
разобрать ограниченное окно событий по ключу **и PID/идентичности** наблюдателя;
одно имя `python3` не доказывает принадлежность измерителю. `probe_pid` в снимке
помогает связать событие с процессом, но PID нужно рассматривать в рамках того же
boot и времени жизни процесса.

После read-only discovery вне нагрузочного окна можно задать необязательный
`guest_process_targets`: список точных `pid`, `comm`, `start_ticks` из свежего
гостевого снимка, вместе с обязательным `guest_process_boot_id` того же снимка.
Targets без boot UUID (или UUID без targets) отвергаются. Список должен покрывать `process_names`; включить все нужные
экземпляры процессов. Не копировать числовые PID из примеров или старой загрузки.
При выбранном режиме гостевой пробник читает только эти процессы и не обходит
весь `/proc`. Пропавший процесс, другое имя или start_ticks означают STOP; нет
обхода проверки после смены boot UUID — это тоже STOP до чтения выбранных PID. Нет
автоматического перехода к полному поиску. После рестарта нужна новая явная
инвентаризация и новый baseline. Хостовой сбор не переключается в гостевые PID.

Те же targets передаются брокеру через `--measurement-config` и фиксируются его
allowlist; новый состав требует нового сеанса. Это оптимизация наблюдателя,
**не исключение Python или `/proc` из EDR**, не выключение защит и не доказательство
нулевого влияния пробника. Остальные чтения и служебные процессы продолжают
создавать аудит. После изменения наблюдателя повторить T20/покой и исходный B;
не сравнивать новый C со старым B как причинный эксперимент.

Версия `auditd_version` теперь означает версию **установленного Debian-пакета**,
прочитанную через `dpkg-query` вместе со статусом `install ok installed`;
происхождение сохраняется в `auditd_package`. Это не доказательство тождества
запущенного процесса пакетному бинарнику. В auditd 3.0.9 нет опции `-v`;
при отсутствии dpkg/пакета версия остаётся неизвестной, без запуска второго daemon.
[CLI auditd в Debian 12](https://manpages.debian.org/bookworm/auditd/auditd.8.en.html).

Единственное распознаваемое неявное действие — `overflow_action=syslog` для
**точно `auditd 1:3.0.9-1`**, если параметр отсутствует в прочитанном конфиге.
Это dispatcher queue в auditd 3, не rsyslog file-forwarder. Значение сохраняется
отдельно в `effective_defaults` с `origin=verified-package-default`, версией,
источником и SHA256 source/patch archives; `auditd_conf` остаётся фактически
прочитанным и не дополняется. Guard сверяет всю эту привязку. Явное unsafe-значение,
неизвестная/модифицированная версия и отсутствие provenance по-прежнему блокируют.
Сверены [Debian DSC](https://deb.debian.org/debian/pool/main/a/audit/audit_3.0.9-1.dsc)
и соответствующие orig/debian archives: в `src/auditd-config.c:351` default —
`O_SYSLOG`, четыре Debian patches его не изменяют. На guest ничего не скачивается.
Это узкое подтверждение package default, не утверждение о текущем состоянии очереди
и не замена проверки нестандартного/vendor-бинарника.

По явному решению оператора исходной точкой является **текущий EDR runtime-профиль**,
включая его правила и kernel controls, а не восстановленный исторический P1.
Измеритель не меняет правила, `auditd.conf` или controls. Допуск принимает
`failure=0` (silent) и `failure=1` (printk); оба не предписывают panic. `failure=2`
и неизвестное/отсутствующее значение блокируют запуск и продолжающийся сбор.
Это исправление смысла availability gate, не автоматическое изменение 0 → 1
и не признание silent loss допустимой: требования `enabled=1`, активного auditd,
`lost=0`, ограничения backlog, диска, температуры и доступности сохранены.
[Значения kernel failure в auditctl](https://manpages.debian.org/bookworm/auditd/auditctl.8.en.html).
Само исправление kernel failure не отключает стоп по отдельным ядрам.

### CPU-полка: предупреждение или остановка

Утверждённый новый пилот `B-EDR-CURRENT` исследует последствия для сервиса,
а не сам факт занятости CPU. До запуска оператор явно задаёт в приватном
measurement JSON `"cpu_action": "warn"`. Допустимые значения — `stop` и `warn`;
если поле отсутствует, действует `stop`, как и в поставляемом шаблоне.
`warn` требует расширенный JSON probe (`--measurement-argv-file`); прежний shell
probe и `traffic-only` не являются обходом этого требования.

При `warn` оба CPU-критерия — длительная высокая загрузка отдельного ядра
host/guest и прежний суммарный CPU NGFW — сохраняют пороги, окна и измерения,
но записывают предупреждение вместо остановки. Снимки сохраняют `warnings`,
а итоговый `summary.json` — историю предупреждений. Панель отличает их от STOP.
Это не исключение целой VM/хоста из наблюдения и не изменение EDR, AuditD или KVM.
Выбор фиксируется до первого окна и остаётся одинаковым в сравниваемых прогонах;
после STOP нельзя менять интерпретацию уже сохранённого результата.

Все остальные проверки остаются остановками: температура, память, диск,
lost/backlog, доступность, задержка контрольного запроса, срок сбора, целостность
rules/config/kernel controls и данных наблюдения. Указанный polling baseline
по-прежнему требует подтверждения идентичности потоков; `warn` не отменяет эту
проверку. Предупреждение не является диагнозом или разрешением игнорировать
последующую деградацию сервиса.

CPU 100% без ухудшения сервиса не доказывает отказ NGFW, а без отдельного
сопоставимого контроля без EDR не доказывает стоимость самого EDR. Улучшение
полезной скорости/задержек при одинаковой CPU-полке описывать отдельно; оно не
подменяет формулу и порог 70% H2. См. [критерии методики](ngfw-audit-performance-plan.md).

### Явно подтверждённые guest busy-poll потоки

Некоторые dataplane-потоки постоянно занимают закреплённое ядро даже без тестового
трафика. Их `busy_pct=100` не измеряет оставшуюся производительность. Это **не**
основание автоматически исключать любое загруженное ядро. По умолчанию прежний
стоп по всем ядрам сохраняется. Для фактически проверенного polling допускается
необязательный `guest_busy_poll_baseline` в приватном measurement JSON:

```json
{
  "boot_id": "ACTUAL-GUEST-BOOT-UUID",
  "observed_seconds": 300,
  "evidence_sha256": "ACTUAL-64-CHAR-LOWERCASE-SHA256",
  "cores": [
    {
      "cpu": "cpu2",
      "pid": 1234,
      "process_start_ticks": 10000,
      "process_comm": "pt-ngfw",
      "tid": 1235,
      "thread_start_ticks": 10001,
      "thread_comm": "ngfw2",
      "affinity": [2]
    }
  ]
}
```

Это содержимое **значения** ключа `guest_busy_poll_baseline`, не отдельный полный
measurement JSON. Числа выше — пример, не значения стенда. Нужны реальные PID/TID,
start ticks, comm, singleton affinity и boot UUID из сохранённого фонового сбора
без генерации; его длительность — 60..86400 секунд. Оператор проверяет содержание
наблюдения и указывает SHA256 артефакта: валидатор проверяет формат привязки,
но не объявляет произвольный хэш доказательством измерения. Не переносить baseline
после перезагрузки/рестарта процессов и не заполнять его по одному статическому CPU%.

Пробник читает только указанные PID/TID (до 16), `/proc`-счётчики, comm/start ticks
и текущую affinity. Нет обхода всех threads, изменения affinity, правил или сервисов.
Идентичность перепроверяется при каждом снимке до исключения **только абсолютного
per-core busy%**. Исчезновение/перезапуск/переименование/смена affinity, остановленный
поток, другая загрузка гостя, неизвестное ядро или исключение всех guest cores дают
STOP независимо от `cpu_action`; хотя бы одно гостевое ядро обязательно остаётся
вне polling-исключения. Все host cores и остальные guest cores остаются под
CPU-контролем с заранее выбранным действием `stop` либо `warn`. Температура,
lost/backlog, AuditD enabled/failure/pid, диск, доступность, задержка, collection
deadline и workload/error guards не меняются. Все исходные CPU-счётчики и derived
ряды остаются в evidence; `busy_poll_baseline.verified_cores` показывает, какие
исключения были реально подтверждены в данном снимке. Это не показатель CPU headroom.
Панель не скрывает эти ядра и их 100%: рядом с ними отображается отметка
подтверждённого polling-фона. Ожидаемое, но не подтверждённое исключение не показывается
как принятое, и runner прекращает нагрузку.

Для H1/H2 polling-профиль должен оставаться неизменным; вывод строится по достигнутой
работе, задержкам/ошибкам, очередям/потерям и составу CPU-time, не по одному busy%.
В `source()` baseline передаётся третьим необязательным параметром; транспорт с
allowlist исходного пробника должен закрепить тот же validated config до соединения.

### Неизменность фактических kernel controls

Допустимые начальные `failure=0` и `failure=1` не означают разрешение переключать
их внутри прогона. Начиная с inventory-before измеритель закрепляет точные
`enabled`, `failure`, `pid`, `rate_limit`, `backlog_limit`, `backlog_wait_time`.
Отсутствующий/нечисловой fixed control блокирует допуск; изменение любого значения
между снимками останавливает прогон, включая переход 0 ↔ 1 и смену auditd PID.
Первый снимок сопоставляется с начальным inventory, а финальный inventory проверяется
отдельно. Таким образом, допустимость EDR baseline не превращается в разрешение
изменять его controls. `backlog`, `lost` и `backlog_wait_time_actual` — динамические
счётчики, они не входят в сравнение fixed controls; прежние lost/backlog stop gates
сохраняются. API `control_changes(before, after)` получает полные guest snapshots;
`Guard(config, initial_guest=inventory_before)` закрепляет исходное наблюдение.

Скопировать [шаблон измерений](templates/ngfw-measurement.example.json) в приватный
каталог и заполнить реальные значения до запуска. Пустые пороги намеренно невалидны.
`guest_disk_devices` должен включать устройство с тем же major:minor, что `audit_fs`;
для layered storage дополнительно выбрать физические устройства, не складывать
их I/O как независимую работу. `host_temperature_keys` — точные ключи discovery,
после reboot их нужно перепроверить. `host_disk_devices` заполнить для анализа H5
на общем хосте. Пределы согласовать с baseline и оборудованием, не брать прошлые 89 °C
как разрешённую температуру. Порог service probe учитывает Docker/SSH/планировщик,
это не пользовательская p95.

### Счётчики отправителя

Перед контрольным A отдельным гостевым playbook apply включить
`ngfw_audit_forwarder_metrics=true` и далее сохранить одинаковым на A/B/C/A.
Default — false; host site playbook не применяет гостевую роль. Только наш
`ngfw-audit-forwarder` перезапускается; AuditD/vendor rsyslog не меняются.
Модуль impstats каждые 5 с пишет JSON только в отдельный локальный ruleset.
`/run/ngfw-audit-forwarder/metrics.jsonl` ротируется при 1 MiB, сохраняется одна
копия `.1`; возможен небольшой выход за порог на текущую запись. Это временные
метрики, не audit.log. Точки ротации и работа измерителя учитываются в T20.
Rollback: повторить apply с false; статистика перестаёт обновляться, старые
временные файлы не являются свежими измерениями. Не применять переключение внутри пары.

## 2. Прогон с привязкой к методике

Заполнить [контекст](templates/ngfw-run-context.example.json): campaign/test/comparison/
workload/profile. Метка профиля ничего не применяет. Формальное сравнение A/B/C
сначала требует фактического применения профиля, T02 и сохранения read-back.
Актуальная изоляция и остальные условия основной методики остаются обязательными.

```bash
python3 runner.py run --audit-profile A \
  --measurement-argv-file /private/guest-probe-argv.json \
  --measurement-config /private/measurement.json \
  --run-context /private/context.json
```

Для B/C использовать также `--baseline /private/completed-A/summary.json` по
[инструкции runner](ngfw-traffic-runner.md). Нагрузку не повышать после STOP.
Расширенный режим и прежний shell probe не используются одновременно. Прежний
режим пока остаётся для воспроизводимости принятых P1-прогонов; он не подходит
новому формальному H2-анализатору. Пересмотр его удаления — после принятия extended T00.

Результат: атомарный `summary.json`, поток `metrics.ndjson`, результаты окон,
`inventory-before/after.json`, SHA256 исполнявшихся измерителей и `manifest.json`.
Финальный manifest появляется только по завершении. Ротация audit.log даёт неизвестную
скорость за пересекающий интервал, не отрицательную/нулевую. Изменившиеся правила или
настройки в течение прогона, потерянный финальный inventory — aborted для сравнения.
Временные снимки не строго одновременны: сохраняются monotonic/wall time/длительность
сбора; сравнивать интервалы, а не порядок появления нескольких миллисекундных событий.

## 3. Реалтайм-интерфейс

Запустить от непривилегированного пользователя, который читает каталог отчётов:

```bash
python3 /srv/apps/ngfw-lab/monitor.py --reports /srv/app-data/ngfw-lab/reports
```

**Использовать фактический `reports_dir` из runner.json**, пример пути выше проверить.
UI слушает только `127.0.0.1:8787`, не требует внешних библиотек/CDN. На Windows:

```powershell
powershell -File scripts/ngfw-access.ps1 -Action TestMonitor -Transport Auto
```

Открыть `http://127.0.0.1:8787/`. `Auto` проверяет аутентифицированный LAN-доступ,
затем Tailscale. Можно выбрать `Local` или `Tailscale`; `-MonitorPort 8788` меняет
только локальный порт туннеля. Host keys не отключаются, host sudo не применяется,
новый сетевой порт не открывается. Запускателя/сервисов этот helper не запускает.
При разрыве SSH туннель перестаёт работать; повторное подключение явное.

Композиция панели:

1. Вверху — выбранный run, test/campaign, профиль, сценарий, повтор, фаза и время,
   состояние и свежесть данных. Активный тест не подменяется архивным без выбора.
2. Четыре карточки — RX конечной точки, CPU NGFW/горячее ядро, температура host,
   backlog/lost AuditD. Температурная карточка — максимум доступных датчиков;
   сам Guard использует только согласованные датчики, не этот общий максимум.
3. Синхронная временная шкала — RX, CPU guest/host, backlog, время контрольной
   проверки. Обновление UI 2 с; частота **новых замеров** определяется runner
   плюс длительностью сбора. Графики ограничены последними 360 отсчётами.
4. Ниже — per-core, disk await/write/queue, audit wait (native units), процессы/wchan,
   очереди rsyslog/счётчики коллектора и пробелы.
5. Таблица завершённых окон — полезная скорость, ошибки/UDP loss и p95 для
   запросов (верхняя граница корзины успешных запросов). Это оконный результат,
   не выдуманная живая p95. RX включает служебные пакеты и не заменяет useful throughput.

CPU-предупреждение показывается отдельно от остановки: занятое ядро/VM остаётся
видимым, но run не получает статус STOP только из-за этого условия в режиме
`cpu_action=warn`. История предупреждений сохраняется и после возвращения CPU
ниже порога; наличие предупреждений не заменяет итог окна и не подтверждает H1/H2.

Нет сырых журналов, SSH argv/конфигов/паролей и кнопок управления. Отсутствующие
значения — «—», разрывы графика, NOT_COLLECTED. Потеря связи не означает STOP нагрузки:
реальную остановку выполняет runner/его watchdog, не web UI. Закрытие браузера
не останавливает тест. При прерывании использовать существующий операторский Ctrl+C
в runner; общие VM/коллектор не останавливать через панель.

### Windows: архив и анализ без нагрузки на сервер

По разрешению владельца Windows-хост можно использовать как рабочее хранилище.
Завершённые каталоги run копировать целиком (с manifest) в приватную
`.ngfw-evidence/reports` внутри локального checkout. Эта папка исключена из Git;
это не шифрование и не резервная копия — права Windows и доступ к устройству
остаются отдельной ответственностью владельца. Сырые журналы автоматически
не копируются. Проверка manifest при анализе выявляет изменившиеся файлы.

```powershell
python roles/ngfw_lab/files/monitor.py --reports .ngfw-evidence/reports
```

Та же панель откроет архив на `http://127.0.0.1:8787/`, без SSH и включённого сервера.
`audit_evidence.py` и `campaign.py` также работают здесь. Live остаётся через туннель:
периодическое копирование всей истории на Windows во время измерения намеренно
не включено, поскольку добавило бы I/O/SSH-помеху. Архив не называется live.

## 4. События и доставка

Анализ выполняется **после опыта** по приватным неизменяемым экспортам одного
guest/boot, включая нужные ротации. Экспорт/передача исходных журналов этим
инструментом не выполняются. Не читать большие логи на NGFW во время сравниваемого
окна. Сохранить способ/полноту экспорта и его временные границы; не выкладывать raw в Git.
Key-map JSON задаёт реальные утверждённые ключи; значения: packet, network_syscall,
exec, file, admin. Угаданные имена/категории не годятся. NETFILTER_PKT определяется
непосредственно; неизвестные записи — unattributed. Связанные PATH/EXECVE наследуют
однозначную группу event. Events считаются по timestamp:serial внутри явного boot scope,
records — отдельно; число events по группам может пересекаться.

```bash
python3 audit_evidence.py summarize --source audit \
  --input /private/audit-export.log /private/audit-export.log.1 \
  --output /private/source-window --scope ngfw-BOOTID \
  --start 1790000000 --end 1790000060 --key-map /private/approved-key-map.json
python3 audit_evidence.py summarize --source collector \
  --input /private/collector-export.jsonl \
  --output /private/receiver-window --scope ngfw-BOOTID \
  --start 1790000000 --end 1790000060 --key-map /private/approved-key-map.json
python3 audit_evidence.py compare \
  --source /private/source-window --receiver /private/receiver-window
```

Числа времени выше — **пример**, заменить реальным epoch-окном `[start,end)`.
Scope и карта групп должны совпадать. Ограничение чтения 256 MiB суммарно,
строка ≤128 KiB; допускается явное повышение до 1 GiB. Большие кампании делить
на объявленные окна. SQLite хранит только digest/ID/тип/группу/размер/время, не raw,
но всё равно является приватным evidence (метаданные и hashes не анонимизация).
Выходной каталог должен быть новым: перезаписи evidence нет. Некорректная строка
создаёт gap. Файл, изменившийся во время чтения, не считается immutable evidence.

Сравнение учитывает копии и непришедшие digest, срезает только syslog-заголовок.
Изменение payload получателем даёт mismatch, а не автоматически потерю. Delivery lag
равен receipt time минус audit time, зависит от синхронизации двух часов; отрицательное
значение не обнуляется. После stop дать очереди дренироваться и зафиксировать предел;
без этого отсутствие записи может означать задержку/неполный экспорт. Оригинальные
NETFILTER/NGFW native события не объединять по предположительному одинаковому ID.

## 5. Численный контроль H2

```bash
python3 campaign.py --a-before /private/A-before --b /private/B \
  --c /private/C-NET --a-after /private/A-after
```

Нужны четыре разных завершённых extended run, одинаковые matrix/topology/observer,
campaign/comparison/workload и ≥3 одинаковых повторов каждого сценария. Проверяются
manifest, стабильные read-back, возврат правил A и неизменная конфигурация auditd/
forwarder. Берутся только интервалы внутри measure window (не warmup/idle), минимум
3 и ≥80% покрытия окна; CPU усредняется по длительности. Работа должна отличаться
не более 5%; добавленная B-нагрузка должна превышать `max(5 п.п., 2 × spread контроля)`.
Снятая доля: `(CPU_B - CPU_C) / (CPU_B - CPU_A_reference) × 100`.

Положительный numeric check **не SUPPORTED**: требуются T11, семантика исключённых
правил, неизменность NGFW/debug/offload, доставка, восстановление и разбор помех.
При нехватке данных инструмент отказывает или пишет конкретные issues, не делает
вывод вместо экспериментатора. H1/H3–H9 оформляются в общем шаблоне с прямыми
ссылками на run и эти evidence; автоматической причинной классификации нет.

## Проверка реализации и источники величин

Portable unit tests: `test_runner`, `test_measurement`, `test_monitor`,
`test_audit_evidence`, `test_campaign`. CI дополнительно проверяет реальные `/proc`,
образ endpoint, syslog-ng CSV и impstats/ротацию в Debian 12 rsyslog. CI не заменяет
проверку этой appliance/гостевого sudo/сопоставимости T20.

Disk await — delta(read_ms+write_ms)/delta(completed reads+writes), 512-byte sectors;
это среднее, не p95 и не полная причинная атрибуция. Источник полей —
[Linux iostats](https://docs.kernel.org/admin-guide/iostats.html).
Счётчики отправителя и влияние их сбора описаны в
[rsyslog impstats](https://docs.rsyslog.com/doc/configuration/modules/impstats.html),
ограничение файлов — в [rsyslog rotation](https://docs.rsyslog.com/doc/tutorials/log_rotation_fix_size.html).
Отсутствующее поле в установленной версии не выводится как ноль.
