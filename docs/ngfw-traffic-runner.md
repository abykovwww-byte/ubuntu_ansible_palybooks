# Автоматические прогоны трафика PT NGFW

Для расширенной методики H1–H9 использовать
[измерители и живую панель](ngfw-measurement-toolkit.md): JSON probe, дополнительные
стоп-условия, read-back, run context, анализ событий и парных сравнений.
Описанный ниже shell probe остаётся для ранее принятых P1-прогонов; сам по себе
не покрывает новые измерения и не даёт допуска ко всем тестам методики.

Последовательность эксперимента и связь **H1/H2 → тест → запуск → вывод**:
[план испытаний AuditD](ngfw-audit-performance-plan.md) и
[шаблон результатов](templates/ngfw-audit-performance-results.md).
Runner выполняет отдельные прогоны; наличие плана не означает автоматическую
смену профилей или готовые выводы по тезисам.

Запускатель находится в `roles/ngfw_lab/files/runner.py`; Ansible устанавливает его
в `/srv/apps/ngfw-lab`. Он выполняет матрицу нагрузки для **одного уже выбранного
состояния AuditD**. Метка `--audit-profile P0` или `P2` попадает в отчёт; правила
AuditD, конфигурация PT и состояние VM автоматически не изменяются.

## Состав и профили

Два контейнера собираются из `roles/ngfw_lab/files/traffic/Dockerfile` на Python
3.12 / Debian 12. На каждом — лимит 1 CPU, 512 MiB памяти, 192 процесса,
read-only файловая система и ограниченный tmpfs. CPU/память и адреса задаются
переменными `ngfw_lab_traffic_*` и `ngfw_lab_*_address` в Ansible.
Сервер слушает TCP 5201 (iperf3), UDP 5201, TCP 9000 (короткие соединения),
TCP 8080 (HTTP) и UDP 5353 (DNS). DNS отвечает только на A-запрос `lab.invalid`
статическим адресом `192.0.2.1`; обращения к внешнему DNS отсутствуют.

| Сценарий | Нагрузка по умолчанию |
| --- | --- |
| tcp-single | 20 Мбит/с, один поток |
| tcp-parallel | 100 Мбит/с суммарно, четыре потока |
| udp-20m / udp-60m / udp-100m | 20 / 60 / 100 Мбит/с, payload 1200 байт |
| udp-small | 20 Мбит/с, payload 64 байта, около 39 063 отправляемых датаграмм/с |
| short-tcp | до 100 новых соединений/с, 8 параллельных работников |
| http | до 100 GET `/health`/с, новое соединение на запрос |
| dns | до 100 UDP-запросов/с |

Это заданная нагрузка, не гарантия достигнутой скорости. Отчёт содержит фактически
полученную скорость/число ответов. Мелкие UDP-пакеты не означают wire-rate генератор;
CPU контейнера или гипервизора может ограничить PPS. Мбит/с относятся к прикладным
данным, без Ethernet/IP overhead. Параметр `iperf3 -b` применяется к каждому потоку,
поэтому запускатель делит суммарную скорость на `-P` — см.
[документацию iperf3](https://software.es.net/iperf/invoking.html).

Для каждого сценария: 120 секунд разогрева → 600 секунд измерения → 180 секунд
простоя. Три повтора. Полная стандартная матрица занимает **6 ч 45 мин** плюс
служебные проверки. Разогрев сохраняется отдельно и не участвует в сравнении
с контрольным прогоном. Для первого smoke-прогона задайте меньшую матрицу и времена
через Ansible; полный контроль и последующий профиль должны использовать одинаковые
настройки. Переменные: `ngfw_lab_traffic_scenarios`, `ngfw_lab_traffic_duration`,
`ngfw_lab_traffic_warmup`, `ngfw_lab_traffic_idle`, `ngfw_lab_traffic_repetitions`.

## Подготовка и проверка маршрута

После обычного Ansible apply файлы и конфигурация установлены, но генерация нагрузки
не запускается. `ngfw_lab_start_traffic: true` собирает образ и поднимает **ожидающие
конечные точки**. Контейнеры имеют `restart: "no"`, чтобы перезапуск Docker не вернул
лабораторию самопроизвольно. Ручной эквивалент после установки файлов:

```bash
cd /srv/apps/ngfw-lab
docker compose up -d --build
python3 runner.py plan
```

На NGFW разрешите перечисленные выше порты из левого сегмента в правый. На обоих
management-адресах должны отвечать настроенные TCP-порты: по умолчанию NGFW 22
(`ngfw_lab_management_port`) и MNGT 443 (`ngfw_lab_mngt_port`). Эти значения нужно
сверить с фактической первичной настройкой PT.
Готовность PT UI и корректность политики проверяются отдельно: открытый TCP-порт
сам по себе не подтверждает работоспособность приложения.

Перед первым запуском оператор выключает NGFW и выполняет:

```bash
python3 runner.py check-isolation
```

Проверка требует `virsh domstate = shut off`, проверяет локальное здоровье
приёмника, затем убеждается, что клиент его не достигает. Свидетельство сохраняется
в `/srv/app-data/ngfw-lab/reports/isolation.json` на 24 часа и привязывается к
образам, ресурсам, сетям, адресам и XML VM. Запускатель не выключает VM сам.
После проверки оператор запускает NGFW и проверяет её готовность. При изменении
топологии или истечении срока отрицательная проверка обязательна снова.

## Выполнение

Для первичной проверки только трафика:

```bash
python3 runner.py run --audit-profile P0 --traffic-only
```

Этот режим **не наблюдает AuditD, CPU и файловую систему гостевой NGFW** и явно
обозначается `traffic-only`. Он не даёт заключения о безопасности настройки AuditD.

Для наблюдения AuditD нужен уже разрешённый в вашей лаборатории SSH-доступ к
NGFW с правами чтения `auditctl -s` и `/var/log/audit/audit.log`. Создайте вне Git
локальный файл аргументов, например `/etc/ngfw-lab/probe-argv.json`:

```json
["ssh", "-T", "-o", "BatchMode=yes", "-o", "ConnectTimeout=2", "-o", "StrictHostKeyChecking=yes", "-i", "/absolute/path/to/lab_key", "root@10.77.0.20", "sh", "-s"]
```

Путь к ключу и учётная запись в примере — заменяемые параметры; разрешения на
appliance нужно согласовать с порядком эксплуатации PT. Не меняйте поддержку
root/sudo специально ради скрипта и не отключайте проверку ключа сервера.
Пароль в аргументы не добавлять. Файл содержит массив аргументов, исполняемый
без локальной shell-интерполяции. Содержимое файла не попадает в отчёт.

`ngfw_probe.sh` передаётся через stdin и только читает состояние; на NGFW не
устанавливаются пакеты или файлы. Отсутствие доступа или обязательных полей
останавливает прогон до нагрузки. Путь audit.log в этой версии фиксирован:
`/var/log/audit/audit.log`; иное расположение потребует изменения пробника.

```bash
python3 runner.py run --audit-profile P0 \
  --probe-argv-file /etc/ngfw-lab/probe-argv.json

# После ручной настройки следующего профиля AuditD:
python3 runner.py run --audit-profile P2 \
  --probe-argv-file /etc/ngfw-lab/probe-argv.json \
  --baseline /srv/app-data/ngfw-lab/reports/CONTROL_RUN/summary.json
```

При сравнении контрольный прогон должен быть завершён и иметь ту же матрицу,
времена, число повторов, пороги и топологию. Для TCP используется медиана
**измерительных** повторов соответствующего сценария. При отсутствии `--baseline`
отчёт отмечает, что падение TCP относительно контроля не проверялось.

## Остановка и данные

В каждом цикле наблюдения проверяются management NGFW/MNGT, состояние VM,
HTTP через dataplane, память/диск хоста и доступность пробника. Интервал задаётся
`ngfw_lab_traffic_sample_interval` (5 секунд); к реакции добавляется ограниченное
время сбора. В режиме AuditD автоматически останавливают нагрузку:

- любое `lost > 0` или смена boot ID;
- backlog не ниже 75% лимита в течение 30 секунд;
- занято не менее 80% root/audit filesystem;
- CPU NGFW не ниже 90% в течение 60 секунд;
- память NGFW или хоста занята не менее 90% в течение 60 секунд;
- наблюдаемый рост журнала 60 секунд подряд предсказывает заполнение менее чем за 24 часа.

Недоступность management/dataplane или VM останавливает прогон на первой неуспешной
проверке. UDP loss выше 0,5% и TCP ниже 80% контрольной медианы проверяются **после
завершения отдельного прогона**, поскольку используются итоговые данные приёмника.
Пороги настраиваются в `ngfw_lab_traffic_limits`. Проверки наличия записей об
административных действиях и анализ ошибок ядра остаются отдельной приёмкой.

Ctrl+C / SIGTERM сохраняет частичный отчёт и завершает только process group
текущего задания. Если связь с Docker нарушена, встроенный watchdog всё равно
ограничивает задание длительностью прогона + 10 секунд. Блокировка предотвращает
параллельные запускатели с одним каталогом отчётов. Ручной посторонний iperf3
в том же контейнере запускать во время матрицы нельзя.

Каждый запуск создаёт уникальную папку под `/srv/app-data/ngfw-lab/reports/`:

- `report.md` — результат, причины остановки, пробелы;
- `summary.json` — параметры, образ, топология, версия iperf3 и результаты;
- `results.csv` — одна строка на разогрев/измерение;
- `metrics.ndjson` — временной ряд с привязкой к сценарию/повтору/фазе;
- `SCENARIO-REPEAT-PHASE.json` и `.stderr` — необработанный результат нагрузки;
- `isolation.json` — свидетельство отрицательной проверки маршрута.

Временной ряд включает `virsh domstats`, Docker CPU/память, host diskstats/vmstat,
состояние AuditD, размер/скорость роста лога. Отчёт по HTTP/TCP/DNS содержит
p50/p95/p99 как **верхние границы гистограммных интервалов**, не точные квантили.
Event serial даёт только оценку EPS; ротация/обнуление serial обозначают пробел,
и оценка не служит доказательством полноты логирования. Сами audit-записи и
командная строка SSH в отчёты не сохраняются. Графики и автоматическая оценка
дисковой задержки из diskstats в этой версии не строятся; сырые значения сохранены.

## Проверки кода

`test_runner.py` проверяет пороги, полноту данных, матрицу, совместимость контроля
и частичные отчёты. `test_runtime.py` в собранном контейнере проверяет настоящий
TCP/UDP/HTTP/DNS обмен на loopback и watchdog. Workflow `NGFW traffic` выполняет
эти проверки в CI. Loopback-тест не подтверждает маршрутизацию через PT NGFW;
она проверяется только на развёрнутом стенде.

## Большие ACL/NAT

Для настройки самой политики PT NGFW есть отдельный
[Ansible playbook и проверки ACL/SNAT/DNAT](ngfw-policy.md).
Он не запускается обычным apply стенда и не публикует правила автоматически.
Дополнительные listeners генератора включаются явно; существующие сценарии
нагрузки и стоп-условия остаются прежними.
