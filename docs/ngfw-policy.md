# Большая лабораторная политика PT NGFW через Ansible

Это конфигурация **самого PT NGFW через API v2 центра управления MNGT**,
не iptables/nftables на гипервизоре. Отдельный playbook:
`playbooks/ngfw-policy.yml`; роль `ngfw_policy`; модуль `pt_ngfw_policy`.
Обычный `site.yml` эту роль **не запускает**, поэтому очередной общий apply
не отправит и не опубликует правила неожиданно. По умолчанию отдельный playbook
строит только офлайн-план, без сети и учётных данных.

## Что входит в стандартный профиль

| Набор | Количество | Условия |
|---|---:|---|
| ACL | **1000** | 5 базовых allow, 2 allow для NAT, 992 портовых правила, завершающий scoped drop |
| SNAT | **100** | TCP 20000–20099; динамический IP+port, адрес выходного интерфейса |
| DNAT | **100** | VIP 10.77.20.100:30000–30099 → 10.77.20.10:8080 |
| Зоны | 2 | `auditd-lab-left`, `auditd-lab-right` |
| Адресные объекты | 3 | клиент, приёмник, VIP, каждый /32 |
| Сервисы | 1199 | TCP/UDP, отдельные порты и два диапазона |

ACL масштабирования используют разные TCP-порты 10000–10991, каждое десятое
правило — DROP. Это не 1000 одинаковых перекрывающих друг друга записей.
Все правила ограничены двумя стендовыми зонами и точными адресами клиента
и приёмника/VIP. Разрешения any-any, доступа в домашнюю LAN или в management
нет. Последний DROP тоже ограничен этими адресами и направлением.
Базовые сервисы сохраняют генератор из PR #147: TCP/UDP 5201, TCP 8080/9000,
UDP 5353. Ответы проверяются в рамках сессий, отдельного широкого reverse allow нет.

Настройки: `acl_count` от 16 до 10000, чётный `nat_count` от 2 до 2000
(половина SNAT, половина DNAT). Это границы **нашего генератора**, не утверждение
о производительности/лицензионных лимитах VM. Начинать приёмку можно с 18/2
(в этом минимальном профиле уже есть портовое DROP-правило),
затем увеличивать до 1000/200. Уменьшение и смена namespace намеренно не удаляют
старые объекты: модуль останавливается для отдельного согласования очистки.

## Источник контракта и граница проверки

Названия методов, полей, enum и вложенных структур проверены по OpenAPI 3.0.3,
API v2, встроенной в заводской MNGT-дистрибутив
`pt-ngfw-mngt-vm-1.11.1-1750-debian-12.qcow2` (backend `f7eebf3c`).
Образ прочитан без запуска и изменения. Бинарники, клиент производителя и полная
схема не распространяются в этом репозитории. Модуль написан независимо.
API доступен в установленном MNGT через `/apidoc/v2`; механизм авторизации описан
в [официальной справке API](https://help.ptsecurity.com/ru-RU/projects/ngfw/1.7/help/8298063371)
(ссылка на общую справку 1.7; точный контракт здесь взят из образа **1.11.1**).

Офлайн-тесты используют контрактный симулятор, не настоящий NGFW. Дополнительный
локальный тест с `NGFW_OPENAPI_SCHEMA=<путь к локальному JSON OpenAPI>` проверяет
все запросы по предоставленной схеме. В CI он пропускается, если схема отсутствует.
Ни проверка схемы, ни зелёный CI не доказывают, что правила принял или установил
живой NGFW. Этот этап требует нижеописанного apply/read-back/publish/packet check.

## Предварительная настройка стенда

1. Инициализировать MNGT и зарегистрировать лабораторный NGFW 1.11.1.
   Создать дочернюю **не корневую** группу `ngfw-auditd-lab` и привязать к ней
   лабораторный виртуальный контекст. Первичная регистрация, лицензирование,
   пароли и создание контекста не входят в эту роль.
2. Подготовить два routing-интерфейса: left `10.77.10.1/24`, right
   `10.77.20.1/24`, включённые, в одном виртуальном маршрутизаторе. Адреса должны
   уже быть именно такими: модуль их проверяет, но не перенумеровывает интерфейсы,
   не создаёт маршруты и не трогает management `10.77.0.20`.
   По умолчанию connected-маршруты достаточны для двух этих подсетей.
3. Получить инвентарь через `mode=discover` и в конфигурации указать точные UUID
   группы, logical/physical device и обоих virtual interfaces из MNGT.
   Автовыбора «первого устройства/порта» нет. Серийный номер устройства не следует
   подставлять вместо API `physical_devices[].id`.
4. Доверить сертификат MNGT или указать `ca_file` на сервере. HTTPS-проверка
   обязательна; перенаправления и системные HTTP-прокси не используются.
5. Не редактировать эту политику из UI/другим API-клиентом во время reconcile.
   От параллельных запусков Ansible на том же сервере защищает локальная блокировка.
   API не предоставляет здесь атомарную транзакцию всех 2404 объектов.

Роль сама создаёт две зоны и привязывает их к **проверенным** lab-интерфейсам.
Существующие чужие объекты не принимает во владение: проверяются имя, namespace,
маркер владельца и device group. Чужие правила в выделенной PRE-группе и активные
унаследованные PRE-правила блокируют запуск, чтобы не скрыть перекрытие правил.
IPS/AV/ICAP и расписания не добавляются; неожиданные профили на управляемых ACL
или default IPS на контексте блокируют baseline, а не игнорируются.

### Если baseline уже существует в Global

Не нужно повторно регистрировать устройство или ослаблять проверку non-root group.
Сначала `discover`: он показывает существующие группы, physical/logical device,
контексты, IPv4/IPv6 интерфейсов, зоны и виртуальные маршрутизаторы. Для этого
режима UUID не требуются. Он выполняет только Login, четыре операции чтения и
Logout; не создаёт группу, не переносит контекст, не меняет ACL/NAT, зоны или IP.
`--check` не превращает discovery в другой режим.

Для существующего контекста в `Global` подготовку дочерней группы и перенос
следует согласовать отдельно, предварительно проверив наследование baseline
и влияние на текущий трафик. Discovery выдаёт предупреждение, а `check/apply`
продолжают требовать явно выбранную non-root группу. Инвентарь не означает
готовность к применению и не является автоматическим файлом overrides.

### HTTPS после настройки LAN-доступа

По умолчанию используется TLS-passthrough из PR #157:
`https://192.168.1.88:8443` → `10.77.0.10:443`. Разрешён именно этот LAN origin,
не произвольный адрес/порт. Для прежнего прямого доступа разрешена изолированная
сеть `10.77.0.0/24` на HTTPS 443, но сертификат обязан соответствовать выбранному IP.
Сертификат только с SAN `192.168.1.88` не подходит для URL `https://10.77.0.10`.

`ca_file` — существующий публичный PEM CA **на Ansible-сервере**, не закрытый ключ
и не путь на Windows. Для лабораторного CA, подготовленного 18.09.2026, это
`/srv/app-data/ngfw-lab/pki/192.168.1.88-20260918/pt-ngfw-lab-root-ca.pem`.
При замене CA оператор обновляет путь. При `ca_file: null` используется системное
хранилище доверия Python. Ни отключения TLS-проверки, ни fallback на HTTP нет.

## Переменные и запуск на сервере

Репозиторий сначала доставляется обычным pull-based процессом. Секреты оператор
задаёт только в серверном `/etc/ansible/local-overrides.yml` (или Ansible Vault).
Не передавать пароль в командной строке, не добавлять его в Git, не присылать в чат.
Параметры `ngfw_policy_login` и `ngfw_policy_password` имеют Ansible `no_log`.

Ниже только **несекретная часть** overrides; UUID заменить своими. Вложенный
словарь может содержать только переопределённые значения: остальные модуль берёт
из собственных defaults. Не сохранять `ngfw_policy_mode: publish` в постоянных
overrides — публикация должна оставаться отдельным осознанным запуском.

```yaml
ngfw_policy_config:
  acl_count: 1000
  nat_count: 200
  management_url: https://192.168.1.88:8443
  ca_file: /srv/app-data/ngfw-lab/pki/192.168.1.88-20260918/pt-ngfw-lab-root-ca.pem
  device_group_name: ngfw-auditd-lab
  device_group_id: REPLACE_FROM_MNGT
  logical_device_id: REPLACE_FROM_MNGT
  physical_device_id: REPLACE_FROM_MNGT
  left_interface_id: REPLACE_FROM_MNGT
  right_interface_id: REPLACE_FROM_MNGT
  dedicated_mngt_confirmed: false
  log_mode: NO_LOG

# Включается только при подготовке контейнеров генератора:
ngfw_lab_policy_listener_ranges: [[10000, 10991], [20000, 20099]]
```

Команды выполняет оператор интерактивно на сервере из актуального checkout.
`sudo` здесь не автоматизируется агентом.

```bash
cd /opt/ubuntu_ansible_palybooks

# Без сети: только план и набор проверочных пакетов.
sudo .venv/bin/ansible-playbook -i inventories/local/hosts.yml playbooks/ngfw-policy.yml \
  -e @/etc/ansible/local-overrides.yml -e ngfw_policy_mode=plan

# Login + инвентарь для выбора UUID; можно запускать до заполнения UUID.
sudo .venv/bin/ansible-playbook -i inventories/local/hosts.yml playbooks/ngfw-policy.yml \
  -e @/etc/ansible/local-overrides.yml -e ngfw_policy_mode=discover

# Login + чтение, никаких изменений конфигурации MNGT.
sudo .venv/bin/ansible-playbook -i inventories/local/hosts.yml playbooks/ngfw-policy.yml \
  -e @/etc/ansible/local-overrides.yml -e ngfw_policy_mode=check

# Создать/обновить candidate; затем независимое повторное чтение всех объектов.
# Снимок НЕ публикуется. Повторный apply должен дать change_count: 0.
sudo .venv/bin/ansible-playbook -i inventories/local/hosts.yml playbooks/ngfw-policy.yml \
  -e @/etc/ansible/local-overrides.yml -e ngfw_policy_mode=apply
```

Ansible `--check` для apply/publish принудительно выполняет только remote check.
Он требует доступного MNGT и заполненных UUID, но не создаёт/обновляет объекты.
На пустом стенде используйте `mode=plan`, если нужен полностью офлайн-просмотр.

Результаты без учётных данных: `/srv/app-data/ngfw-lab/policy/plan.json` и
`plan-result.json`, `discover-result.json`, `check-result.json`, `apply-result.json`,
`publish-result.json`. Discovery дополнительно сохраняет `discovery.json`: только
разрешённые поля, без полных API-ответов, описаний и cookies. Это всё равно
инвентарь инфраструктуры: держать локально, не публиковать в GitHub. Каталог имеет
права 0750, файлы 0640. `changed: false` модуля в discovery означает отсутствие
изменений MNGT; роль может создать/обновить локальные файлы результатов.
`plan_sha256` связывает результат с конкретным планом. Списки читаются полностью:
offset для объектов, cursor/nextCursor для ACL/NAT. Повторная страница, дубликаты,
ошибка или неподтверждённое read-back завершают операцию ошибкой.
Автоповторов изменяющих запросов и автоматического удаления нет. После обрыва
сначала `check`, затем восстановительный `apply`; изменения candidate могли
выполниться частично. Не запускать слепую повторную публикацию после тайм-аута job.

## Отдельная публикация

**CommitSnapshot/PushSnapshot глобальны для MNGT.** Даже при одном NGFW в снимок
попадают другие накопленные candidate-изменения. Перед публикацией проверить их
в UI, отсутствие посторонних правок и подтвердить, что MNGT выделен только этому
стенду. Затем оператор меняет `dedicated_mngt_confirmed: true` в private overrides
и явно запускает:

```bash
sudo .venv/bin/ansible-playbook -i inventories/local/hosts.yml playbooks/ngfw-policy.yml \
  -e @/etc/ansible/local-overrides.yml -e ngfw_policy_mode=publish
```

Модуль требует ровно один physical device с ожидаемым UUID, сначала проверяет
совпадение candidate с планом, создаёт snapshot с `push: false`, ждёт commit job,
потом отправляет **именно полученный snapshotId** и ждёт push job. Успех требует
отсутствия failed targets и подтверждения ожидаемого имени NGFW. Это явная
операция публикации, не идемпотентный reconcile: повторный publish создаст новый
снимок. После тайм-аута сначала проверить существующий job в MNGT.

`push-job-confirmed` означает отчёт MNGT об установке, а не проверку прохождения
пакетов и не доказательство попадания во все 1200 правил.

## Проверка трафиком и связь с AuditD

Дополнительный приёмник в traffic-server включается переменной
`ngfw_lab_policy_listener_ranges`. По умолчанию список пуст, дополнительные порты
не слушаются. Значение для выбранного размера находится в `plan.json.receiver_ranges`.
После изменения диапазонов нужен обычный Ansible apply роли `ngfw_lab` с
`ngfw_lab_start_traffic: true`, чтобы пересоздался контейнер.
Один selector-поток обслуживает все порты, максимум 128 одновременных соединений,
1024 байта входа и 2 секунды ожидания на клиента; нагрузка сама не запускается.
Контейнер остаётся read-only, без capabilities, с CPU/memory/pids-ограничениями.

Сначала подтвердить отсутствие обходного пути по инструкции
[генератора](ngfw-traffic-runner.md). Затем выполнить короткие пробы:

```bash
cd /srv/apps/ngfw-lab
# Независимо проверить все ожидаемые listeners внутри приёмника.
docker compose exec -T traffic-server python3 /opt/traffic/policy_probe.py listeners \
  < /srv/app-data/ngfw-lab/policy/plan.json
# Первое/среднее/последнее правило каждого типа, плюс DROP.
docker compose exec -T traffic-client python3 /opt/traffic/policy_probe.py check \
  < /srv/app-data/ngfw-lab/policy/plan.json
```

Ответ содержит случайный nonce, фактический source IP, локальный destination IP
и порт. Для SNAT ожидается `10.77.20.1`, для DNAT — приёмник `10.77.20.10:8080`.
Перед проверкой DROP и после тайм-аута проверяется базовый разрешённый путь.
Тайм-аут сам по себе **не доказывает**, какое правило отбросило пакет: поле
`deny_attribution_inconclusive` это явно отмечает. Счётчики попаданий конкретных
правил проверить в MNGT отдельно. `rule_hits_verified` автоматически не становится true.
Проверочные пробы — выборка, не нагрузочный тест каждого правила.

Исходный runner продолжает нагрузку базовых сервисов; правила масштаба добавляют
размер таблицы, а новые пробы проверяют её разные участки. AuditD-профили P0/P1/…
сравнивать при неизменных ACL/NAT и неизменном логировании firewall. По умолчанию
`NO_LOG`: это настройка журналирования **сетевых сессий**, не выключение AuditD.
При отдельном сравнении session logging можно выбрать `AT_SESSION_END`; нельзя
одновременно менять этот режим, размер таблицы и AuditD и затем приписывать
разницу только AuditD. [Основной план испытаний](ngfw-auditd-pilot.md).
