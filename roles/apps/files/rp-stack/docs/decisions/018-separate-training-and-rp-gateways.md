# Decision 018: Разделить Training и RP Gateway

Date: 2026-08-08 · Переоформлено 2026-08-09 в формат ADR + execution brief.

## Status

Proposed. Направление принято; Decision 019 выполнил подготовительный этап:
предметный legacy Awareness удалён из общего Gateway, а снятие narrative
validator из RP выполняется после зелёного integration gate. Разделение
процессов и Compose topology ещё не начато. В
`roles/apps/templates/rp-stack.compose.yml.j2` по-прежнему один
сервис `rp-gateway` (контейнер `rp-stack-gateway`), оба GUI зависят от него
через `depends_on`, `OutputValidator` и `safe_fallback` импортируются в общем
пути `app/main.py` и `app/services/adjudicator.py`, а `Adjudicator.__init__`
создаёт валидатор безусловно. API routing и Compose topology не изменены.

## Контекст

Один Gateway сейчас обслуживает разные по смыслу режимы через общий turn
pipeline и условные ветви. Для `training` строгая проверка ответа необходима:
расписание, структура, scoring, скрытые правила, интерактивные поверхности и
authored fallback должны оставаться детерминированными.

Для `rp` тот же подход ухудшает пользовательский опыт. Post-generation
`OutputValidator`, repair-вызовы и `safe_fallback` увеличивают задержку и могут
заменить пригодный художественный ответ общим шаблоном. Смена narrator model не
помогает, если подмена происходит в Gateway после завершения provider call.

Инцидент в длинной RP-партии показал дополнительный риск общей ветки: предметный
предикат финального хода Awareness не проверял `scenario_type` и был применён к
RP после десятого хода. Реальный ответ LLM заменялся `safe_fallback`, после чего
валидатор признавал уже шаблон валидным. Decision 019 удаляет сам предметный
предикат до снятия RP-валидатора. Разделение процессов остаётся нужным по
остальным причинам, но само по себе не исправило бы предикат, перенесённый
вместе с RP pipeline.

У этой недостаточности есть конкретный механизм, который стоит назвать явно.
В коде сосуществуют два разных понятия режима: `settings.scenario_type` —
процессный, из переменной окружения `SCENARIO_TYPE` со значением по умолчанию
`rp` (`rp-gateway/app/core/config.py`), и `party.scenario_type` — на партию
(`rp-gateway/app/main.py`). Разные модули читают разные из них. Пока процесс
один, эти два понятия могут расходиться внутри одного запроса, и любая ветвь,
опирающаяся не на то из них, становится каналом утечки режима.

## Решение

### 1. Разделить runtime-границы

Целевое состояние содержит два независимо развёртываемых Gateway runtime:

- **RP Gateway** обслуживает `scenario_type=rp` и оптимизирует поток для
  непрерывной генеративной игры;
- **Training Gateway** обслуживает `scenario_type=training` и исполняет строгий
  WorldPack-owned training contract.

Это должно быть разделение процессов и turn pipelines, а не новый набор ветвей
в одном `Adjudicator`. Каждый runtime обязан отклонять неподдерживаемый
`scenario_type`. Клиенты должны сохранить совместимый party-scoped API; точный
механизм маршрутизации и миграции будет выбран в плане реализации.

Общие auth, party identity, storage schema и provider plumbing разрешено
переиспользовать без предварительного выделения нового framework или общей
абстракции. Код разделяется только там, где этого требует реальный второй
runtime.

### 2. Удалить narrative validator из RP

В RP Gateway после успешного provider response:

- не вызывается `OutputValidator` для художественного текста;
- не выполняется validation repair completion;
- не используется `safe_fallback` или иной шаблон, маскирующий ответ модели;
- непустой текст narrator сохраняется и возвращается игроку без семантической
  постпроверки и переписывания.

Проверка HTTP/provider payload, разбор формата ответа и защита от пустого
transport response остаются технической границей протокола, но не являются
narrative validation. Ошибка или timeout провайдера возвращаются как явная
ошибка, а не как фиктивный успешный игровой ход.

До вызова модели сохраняются существующие детерминированные механизмы RP:
RuleEngine, canonical state patch и `AUTHORITATIVE_OUTCOME`. Они остаются
источником фактов мира и prompt-контрактом, но Gateway не пытается после
генерации эвристически доказывать, что художественный текст им соответствует.

### 3. Сохранить строгий Training pipeline

Training Gateway сохраняет schema validation, hard/soft constraints,
ограниченный repair, deterministic scoring, authored fallback и проверку
интерактивных artifacts/workspace. Эти механизмы не должны импортироваться или
вызываться из RP Gateway.

## Инварианты

Проверяемые свойства целевого состояния. Ревью реализации проводится против
этого списка, а не против отчёта исполнителя.

1. **Один narrator call в RP.** RP-ход делает не более одного narrator
   completion и возвращает полученный непустой текст без `OutputValidator`,
   repair и `safe_fallback`.
2. **Провал провайдера — это провал.** Ошибка или timeout провайдера в RP
   возвращаются как явная ошибка, а не как HTTP `200` с шаблонным текстом.
3. **Взаимная изоляция кода.** RP runtime не импортирует и не вызывает
   training validation, scoring, authored fallback и artifact/workspace checks;
   training runtime сохраняет их полностью и без ослабления.
4. **Отказ от чужого режима.** Каждый runtime отклоняет `scenario_type`, который
   не обслуживает, — явной ошибкой, а не молчаливой обработкой по своей ветке.
5. **Одно понятие режима на процесс.** После разделения `settings.scenario_type`
   и `party.scenario_type` не могут расходиться внутри обработки одного
   запроса: расхождение — это отказ по инварианту 4, а не выбор ветви.
6. **Сохранение сквозных гарантий.** Idempotency, canonical state, raw history,
   branch isolation и party-scoped публичный API остаются неизменными для
   клиентов по обе стороны разделения.
7. **Единственный писатель данных.** Ни одна таблица не получает второго
   пишущего процесса без явно принятого решения о владении (см. B.6).
8. **Честная телеметрия.** RP получает `transport_status`. Метаданные
   `validator_valid`, `repaired`, `fallback` остаются один релиз как deprecated
   для окна сравнения, после чего удаляются отдельным изменением.

## Не выбрано

- Усилить RP-валидатор дополнительными regex или эвристиками.
- Добавить ещё одно исключение `scenario_type == "rp"` в общий pipeline как
  постоянную архитектуру.
- Оставить шаблонный RP fallback ради HTTP `200`.
- Добавить новую dependency или общий framework до появления повторяемого
  интерфейса между двумя runtime.

## Проверка и доказательства

- Тест длительной RP-партии: после десятого хода нет Awareness/Training ветвей
  и нет шаблонных ответов.
- Training-набор тестов проходит без ослабления существующих гарантий.
- Оба runtime отклоняют чужой `scenario_type`.
- Продакшен-замер до и после: доля RP-ходов с `fallback` и `validator_valid`
  в `turns.metadata_json`, и события `llm_safe_fallback` в `audit_events`.
- Локальная, pushed, applied и live-verified стадии сообщаются отдельно.

## Последствия

### Положительные

- RP получает один прямой narrator path без лишнего repair latency.
- Gateway перестаёт выдавать шаблонную заглушку как успешный RP-ответ.
- Training-регрессии не могут активироваться в RP только из-за номера хода,
  campaign ID или ошибочного условного выражения.
- У каждого runtime появляется собственный набор тестов, fallback policy и
  эксплуатационных сигналов.

### Компромиссы и риски

- RP narrator сможет вернуть слабый, противоречивый или содержащий служебный
  текст ответ; этот риск принимается в пользу непрерывности игры, меньшей
  задержки и отсутствия ложных шаблонных успехов.
- Разделение потребует маршрутизации, независимых health checks, Compose/IaC
  изменений и миграционного периода.
- Общая SQLite authority и party API потребуют явного решения о единственном
  writer либо безопасном разделении владения данными до реализации двух
  процессов.
- Метаданные `validator_valid`, `repaired`, `fallback` для RP потребуется
  удалить, сделать неприменимыми или заменить транспортными статусами без
  сохранения ложной совместимости.

## B.6 Boundaries и открытые вопросы

Ветка `codex/018-mode-isolation`, не пушить в `main`. Не трогать
`app/services/validator.py` и training-пути в Wave A — это только измерение.

Четыре вопроса требуют решения **пользователя**, не Codex. Рекомендации ниже —
мнение Claude, не принятое решение.

1. **Куда отнести `novel` — к RP runtime или в отдельный третий?**
   *Рекомендация: к RP runtime* — у novel нет детерминированного scoring, а
   третий процесс утраивает стоимость топологии ради конфигурационной разницы
   бюджета контекста. Слабая уверенность: решается тем, есть ли у novel
   собственные post-generation проверки — это покажет A2.
2. **Где выполнять маршрутизацию `/api/parties/{party_id}/...` без изменения
   публичного API?** *Рекомендация: решать после A2.* Соответствие
   party → scenario_type авторитетно хранится в SQLite, поэтому маршрутизатор
   обязан читать его оттуда, а не угадывать по пути запроса; конкретное место
   зависит от того, сколько кода до маршрутизации уже опирается на режим.
3. **Как разделить владение фоновыми jobs, provider profiles и общей SQLite?**
   Самый рискованный вопрос. Два процесса, пишущих в один файл SQLite на общем
   volume, нарушают инвариант 7. *Рекомендация: по отдельной БД на runtime*,
   но это решение нельзя принимать без списка таблиц, к которым обращаются оба
   режима, — Claude его не измерял.
4. **Как мигрировать активные партии без переписывания raw turns, state history
   и branch identity?** Прямо следует из ответа на (3). Пока он открыт, ответа
   нет.

# Part C — Verification Codex must perform

Каждое утверждение сопровождается стадией: *local edit · tested · committed ·
pushed · Ansible-applied · container-tested · HTTP-verified · browser-verified.*

## C.1 Static and focused

1. Фокусные тесты по полосам, с точной командой.
2. `powershell.exe -File scripts/ci.ps1` перед публикацией.
3. `python scripts/validate-repository.py`.

Использовать связанные runtime, не `python` из PATH:
`%USERPROFILE%\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe`

## C.2 Prove the guards actually fire

Для A1 доказательство обратное обычному: тест должен **падать** на текущем коде,
если утечка режима воспроизводима. Приложи вывод падения. Если тест зелёный
сразу — объясни, чем он отличается от условий инцидента, прежде чем считать
проблему отсутствующей.

Для будущей проверки инварианта 4 (отказ от чужого `scenario_type`): подай
партию чужого режима, покажи явную ошибку, откати, покажи зелёный прогон.

Отдельно скажи, что именно утверждает каждый положительный тест. Тест, который
скармливает authored fallback валидатору, ради удовлетворения которого этот
fallback и написан, не доказывает ничего.

## C.3 Deploy

Wave A ничего не деплоит — это тесты и документы.

Для Wave B/C: `commit -> push -> ansible-local-apply -> runtime verification`.
`sudo` требует интерактивного пароля, поэтому Codex останавливается на стадии
**pushed** и просит пользователя выполнить:

```bash
sudo systemctl start ansible-local-apply.service
```

Затем: подтвердить завершение сервиса, пересборку контейнеров обоих runtime,
успешные независимые health checks и ответ изменённых эндпоинтов по HTTP.
